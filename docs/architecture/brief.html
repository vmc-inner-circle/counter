한 줄: 가게마다 에이전트용 창구 URL 하나.
손님이 어떤 AI를 쓰든 그 주소 하나로 들어온다.
서버는 방문자가 읽을 수 있는 형태로만 바꿔서 답한다 (사람·브라우저 → 웹페이지, 에이전트 → 마크다운).

오늘 결론 3개
① 프로토콜(작업 상태·슬롯 홀드·기억)은 우리 것 — 이미 서버에 있다
② 손님 쪽 설정은 0 — 주소만 알면 된다. MCP는 커넥터 등록이 필요해서 선택 사항으로 내림
③ 성능은 전송 방식이 아니라 왕복 횟수로 줄인다 (5턴 → 3턴)

웹페이지·마크다운은 같은 주소가 내주는 두 가지 "모양"이지 별도 주소가 아니다. 질문·예약은 둘 다 같은 코어로 간다.
🆕 = 이번에 추가 · ✅ = 오늘 반영(app/ 이동, ADMIN_TOKEN)

2에이전트별로 어디까지 되나

기준: 심사위원이 원래 쓰던 에이전트에 URL 하나만 주면 되는가

에이전트읽기
UC-1		질문·예약
UC-2·3		같은 주소가 내주는 모양
터미널 (Claude Code·Codex)✅✅ 실측함마크다운 → API 호출 (지금 방식)
브라우저형 (Muse·Dots·Pickle·Grok Bot)✅✅ 폼 추가 시웹페이지 → 폼
일반 채팅 (웹 열람만)✅⚠️ 미검증마크다운 → 링크 따라가기 (막힐 수 있음)
요약: 읽기는 누구나. 쓰기는 터미널·브라우저 에이전트까지 설정 없이. 손님이 쓰는 4종은 모두 브라우저형 → 웹페이지 예약 폼이 핵심. 실측 전엔 미검증.

3예약 한 건이 흐르는 길

UC-2(모르는 질문) + UC-3(예약) · wait를 붙여 한 번에 받는 개선안

4성능 — 어디서 시간이 드나

11/09 실측: 전체 26초 (Claude Code)

에이전트가 생각하는 시간 ≈16초
사장님 응답 ≈10초
HTTP냐 MCP냐에서 나는 전송 차이: 밀리초 단위라 막대에 안 보인다 · 분해는 추정(미검증)

지금개선안
왕복문서 → ask → 대기 → book → 대기 = 5턴문서 → ask(wait) → book(wait) = 3턴
예상26초약 20초 이하 미검증 · 구현 후 재실측
전송 방식을 우리가 새로 만들어도 줄어드는 건 밀리초. 줄일 수 있는 건 턴 수뿐이고, 이건 어느 입구로 와도 똑같이 적용된다.

5작업 상태 — 우리 프로토콜의 핵심

stateDiagram-v2
  direction LR
  [*] --> completed: 아는 질문 (기억·등록 정보)
  [*] --> input_required: 모르는 질문 / 예약 요청
  input_required --> completed: 사장님 답변 · 승인
  input_required --> rejected: 사장님 거절
  completed --> [*]
  rejected --> [*]
  note right of input_required
    예약이면 슬롯을 잡아 둔다
    승인 없이는 확정되지 않는다
  end note

상태 이름이 A2A 표준과 같다 → 영상 대본 소재로 활용 가능. 실제 A2A 입구는 이번에 만들지 않는다(쓰는 에이전트가 거의 없음).

6리스크와 대응

리스크대응
심사위원이 아무나 승인·답변ADMIN_TOKEN 잠금 — 반영 완료
사장님 화면에 응답할 사람이 없으면 에이전트가 60초 뒤 멈춤심사 시간 동안 팀원 1명이 폰으로 /admin 담당
앞 심사위원이 슬롯을 잡아 다음 사람이 못 씀/admin 초기화 버튼 (이미 있음)
링크 미리보기·크롤러가 GET 예약 링크를 눌러 버림승인 없이는 확정 안 됨 → 피해 없음
일반 채팅이 GET 링크를 안 따라감배포 전 실측 → 안 되면 표에서 빼고 터미널·브라우저 경로로 안내
